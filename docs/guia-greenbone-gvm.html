Chuleta Greenbone (GVM / OpenVAS) en Kali Linux

Instalación, servicios, actualización de feeds, verificación y reparación.

Referencia: metapaquete Kali gvm 25.04.x (septiembre 2026). Todos los comandos se ejecutan en una terminal de Kali.

Convenciones

  • sudo runuser -u _gvm -- COMANDO = ejecuta el comando como el usuario del servicio _gvm (el que debe ser dueño de los datos de GVM). Es la forma segura de correr las herramientas de GVM.
  • Cuando uses sudo directamente con greenbone-feed-sync, el programa cambia solo a _gvm; ambas formas funcionan.
  • Web UI: https://127.0.0.1:9392 (certificado autofirmado, acepta la advertencia).
  • Ante cualquier duda de opciones: COMANDO --help es la fuente de verdad de tu versión instalada.

1. Instalación inicial

sudo apt update && sudo apt full-upgrade -y

Actualiza Kali antes de instalar (evita conflictos de versiones).

sudo apt install gvm -y

Instala el metapaquete: gsad (web), gvmd (gestor), openvas-scanner (motor de escaneo), ospd-openvas (puente entre gvmd y el scanner), notus-scanner y utilidades.

sudo gvm-setup

Configura todo: arranca PostgreSQL, crea certificados, crea la base de datos gvmd, crea el usuario admin con contraseña aleatoria (anótala) y lanza la primera sincronización de feeds. Tarda de 20 a 60+ minutos. Es seguro volver a ejecutarlo: si algo ya existe, lo detecta y lo omite.

sudo gvm-check-setup

Revisa que la instalación esté completa. Si algo falta, imprime líneas FIX: con el comando exacto para corregirlo; aplícalo y vuelve a ejecutar el chequeo hasta que diga que está OK.

sudo gvm-start

Levanta los servicios y abre el navegador en la web UI.

Nota: gvm-setup termina antes de que gvmd termine de importar los feeds a la base de datos. Hasta que termine, no existen scan configs como "Full and Fast". Mira la sección 4 ("Contenido importado en la base de datos") para comprobarlo.

2. Servicios: levantar, detener, estado

Atajos de Kali

sudo gvm-start      # levanta los servicios de GVM
sudo gvm-stop       # detiene gsad, gvmd, ospd-openvas y notus-scanner

Con systemctl (control fino)

Servicios de GVM: gsad, gvmd, ospd-openvas, notus-scanner. Dependencias: postgresql, redis-server@openvas, mosquitto (los nombres de Redis/MQTT pueden variar según tu Kali; revisa con systemctl list-units | grep -Ei 'redis|valkey|mosquitto').

sudo systemctl start postgresql
sudo systemctl start redis-server@openvas
sudo systemctl start mosquitto
sudo systemctl start ospd-openvas notus-scanner gvmd gsad

Orden recomendado de arranque: primero base de datos y mensajería, luego el scanner, luego gvmd, al final la web.

sudo systemctl stop gsad gvmd notus-scanner ospd-openvas

Detiene en orden inverso (web primero, scanner al final).

sudo systemctl restart ospd-openvas gvmd

Reinicia scanner y gestor; útil después de actualizar feeds. Interrumpe los escaneos en curso.

systemctl status gvmd ospd-openvas gsad notus-scanner
systemctl is-active gvmd ospd-openvas gsad notus-scanner

Estado detallado / estado resumido (active o inactive).

sudo systemctl enable postgresql redis-server@openvas mosquitto ospd-openvas notus-scanner gvmd gsad
sudo systemctl disable ospd-openvas notus-scanner gvmd gsad

Activa o desactiva el arranque automático con el sistema (por defecto en Kali están desactivados).

3. Actualizar feeds manualmente (uno por uno)

Todo se hace con greenbone-feed-sync y su opción --type. Los scripts viejos (greenbone-nvt-sync, greenbone-scapdata-sync, greenbone-certdata-sync) están obsoletos; si los viste en guías antiguas, esta es la equivalencia:

Comando viejo (obsoleto) Comando actual
greenbone-nvt-sync greenbone-feed-sync --type nvt
greenbone-scapdata-sync greenbone-feed-sync --type scap
greenbone-certdata-sync greenbone-feed-sync --type cert
gvm-feed-update (wrapper de Debian/Kali, no mantenido por Greenbone) greenbone-feed-sync (sin argumentos = todo)

Todos los feeds de una vez

sudo runuser -u _gvm -- greenbone-feed-sync

Equivale a --type all. Descarga todo en el orden correcto.

Cada feed por separado

sudo runuser -u _gvm -- greenbone-feed-sync --type nvt

NVT = los tests de vulnerabilidad (agrupa nasl + notus). Reemplaza al viejo greenbone-nvt-sync.

sudo runuser -u _gvm -- greenbone-feed-sync --type nasl

Solo los scripts NASL (los tests clásicos de detección). Destino: /var/lib/openvas/plugins.

sudo runuser -u _gvm -- greenbone-feed-sync --type notus

Solo datos de Notus (detección rápida de paquetes vulnerables del sistema operativo, sin escaneo activo). Destino: /var/lib/notus. Si falta, notus-scanner falla con "/var/lib/notus/products is not a directory".

sudo runuser -u _gvm -- greenbone-feed-sync --type scap

SCAP: base de CVE, CPE y puntuaciones CVSS. Destino: /var/lib/gvm/scap-data. Sin esto los reportes no traen datos de CVE.

sudo runuser -u _gvm -- greenbone-feed-sync --type cert

CERT: avisos de seguridad CERT-Bund y DFN-CERT. Destino: /var/lib/gvm/cert-data.

sudo runuser -u _gvm -- greenbone-feed-sync --type gvmd-data

Datos de gvmd: listas de puertos, scan configs ("Full and Fast", etc.) y formatos de reporte. Destino: /var/lib/gvm/data-objects/gvmd. Si "Full and Fast" no aparece, es este.

Subconjuntos de gvmd-data (si solo necesitas una parte):

sudo runuser -u _gvm -- greenbone-feed-sync --type scan-config
sudo runuser -u _gvm -- greenbone-feed-sync --type port-list
sudo runuser -u _gvm -- greenbone-feed-sync --type report-format

Scan configs / listas de puertos / formatos de reporte, por separado.

Algunas guías escriben los tipos en mayúsculas (--type SCAP, --type GVMD_DATA). Si uno da error de "invalid choice", prueba la otra forma. Valores válidos según la documentación: all, nvt, nasl, notus, scap, cert, gvmd-data, scan-config, port-list, report-format.

Orden sugerido si actualizas a mano por partes

  1. --type nvt (o nasl y notus)
  2. --type scap
  3. --type cert
  4. --type gvmd-data

Opciones útiles de greenbone-feed-sync

sudo runuser -u _gvm -- greenbone-feed-sync --help          # todas las opciones
sudo runuser -u _gvm -- greenbone-feed-sync -vvv            # modo muy detallado (depurar)
sudo runuser -u _gvm -- greenbone-feed-sync --quiet         # sin salida (para automatizar)
greenbone-feed-sync --version                               # versión de la herramienta

Archivos de configuración opcionales (para cambiar URLs o destinos): /etc/gvm/greenbone-feed-sync.toml o ~/.config/greenbone-feed-sync.toml.

Después de sincronizar

sudo systemctl restart ospd-openvas gvmd

Fuerza a recargar los VTs nuevos. Normalmente se recargan solos; usa esto si la web sigue mostrando datos viejos. Recuerda que gvmd importa los datos a la base de datos en segundo plano, y puede tardar un buen rato (Administration → Feed Status en la web muestra el avance).

Problemas al sincronizar

timeout 8 bash -c 'exec 3<>/dev/tcp/feed.community.greenbone.net/873' && echo "rsync alcanzable" || echo "puerto 873 bloqueado"

Comprueba que sales por el puerto 873/tcp (rsync). Si está bloqueado por firewall o proxy, la sincronización falla.

pgrep -af greenbone-feed-sync

Si ya hay otra sincronización corriendo, la nueva se queda esperando o falla por el lock (/var/lib/openvas/feed-update.lock). Solo borra ese archivo si no hay ningún proceso corriendo:

sudo rm -f /var/lib/openvas/feed-update.lock

Automatizar una vez al día

sudo tee /etc/cron.d/gvm-feed-sync >/dev/null <<EOF
30 3 * * * _gvm $(command -v greenbone-feed-sync) --quiet
EOF

Sincroniza todos los feeds cada día a las 03:30 como usuario _gvm (requiere el servicio cron instalado y activo). Con systemd, el script gvm-toolkit.sh autoupdate on crea un timer equivalente. Una vez al día es suficiente; no abuses del servidor del feed.

4. Verificación del sistema

sudo gvm-check-setup

Chequeo oficial de Kali. Debe terminar diciendo que la instalación está OK.

sudo runuser -u _gvm -- gvmd --get-scanners

Lista los scanners registrados. Debe aparecer algo como: 08b69003-5fc2-4037-a479-93b440211c73 OpenVAS /run/ospd/ospd-openvas.sock 0 OpenVAS Default

sudo runuser -u _gvm -- gvmd --verify-scanner=08b69003-5fc2-4037-a479-93b440211c73

Hace que gvmd hable realmente con el scanner. Si responde con la versión de OpenVAS, la cadena gvmd → ospd-openvas funciona. Si falla justo después de arrancar, espera unos minutos: ospd-openvas está cargando los VTs.

sudo runuser -u _gvm -- gvmd --get-users --verbose

Lista usuarios con su UUID.

curl -ks -o /dev/null -w '%{http_code}\n' https://127.0.0.1:9392/

Prueba que la web responde (esperado: 200, 301, 302 o 303).

ss -ltnp | grep -E '9392|5432|1883'

Muestra qué escucha en: 9392 (web GSA), 5432 (PostgreSQL), 1883 (MQTT/Mosquitto).

ls -l /run/gvmd/gvmd.sock /run/ospd/ospd-openvas.sock

Comprueba que existen los sockets de gvmd y ospd-openvas.

redis-cli -s /run/redis-openvas/redis-server.sock ping

Debe responder PONG. Verifica el Redis que usa el scanner. (Si usas Valkey, el cliente es valkey-cli.)

pg_isready
pg_lsclusters

Estado de PostgreSQL / lista de clústeres (versión, puerto, online o down). Si hay más de un clúster tras una actualización, GVM debe usar el del puerto 5432.

Versiones

dpkg -l | grep -E 'gvm|gsad|openvas|ospd|notus'
sudo runuser -u _gvm -- gvmd --version
gsad --version
openvas --version
ospd-openvas --version

Contenido importado en la base de datos

sudo runuser -u _gvm -- psql -d gvmd -tAc "SELECT count(*) FROM nvts;"
sudo runuser -u _gvm -- psql -d gvmd -tAc "SELECT count(*) FROM configs;"
sudo runuser -u _gvm -- psql -d gvmd -tAc "SELECT count(*) FROM port_lists;"
sudo runuser -u _gvm -- psql -d gvmd -tAc "SELECT count(*) FROM scap.cves;"
sudo runuser -u _gvm -- psql -d gvmd -tAc "SELECT count(*) FROM cert.cert_bund_advs;"

Cuentan: VTs, scan configs, listas de puertos, CVEs y avisos CERT. Si alguno da 0, ese feed aún no se sincronizó o importó (ver secciones 3 y 8).

Fecha del feed en disco

grep PLUGIN_SET /var/lib/openvas/plugins/plugin_feed_info.inc

Muestra la versión del feed NASL en formato AAAAMMDDhhmm. Si tiene más de una semana, actualiza.

ls -la /var/lib/openvas/plugins /var/lib/notus /var/lib/gvm/scap-data /var/lib/gvm/cert-data /var/lib/gvm/data-objects/gvmd

Verifica que las carpetas de cada feed no estén vacías.

5. Usuarios

sudo runuser -u _gvm -- gvmd --user=admin --new-password='NUEVA_CONTRASEÑA'

Cambia la contraseña de un usuario existente.

sudo runuser -u _gvm -- gvmd --create-user=analista --password='CONTRASEÑA' --role=Admin

Crea un usuario (roles: Admin, User, etc.).

sudo runuser -u _gvm -- gvmd --delete-user=analista

Elimina un usuario.

sudo runuser -u _gvm -- gvmd --get-users --verbose

Lista usuarios y UUID (necesitas el UUID de admin en la sección 8).

Las contraseñas pasadas por línea de comandos quedan visibles un instante en ps y en el historial del shell. Úsalo solo en equipos de confianza.

6. Certificados TLS

sudo runuser -u _gvm -- gvm-manage-certs -a -f

Regenera todos los certificados (CA, servidor, cliente) sobrescribiendo los existentes. Es el FIX típico cuando gvm-check-setup dice "No CA certificate file".

openssl x509 -in /var/lib/gvm/CA/servercert.pem -noout -dates
openssl x509 -in /var/lib/gvm/CA/cacert.pem -noout -dates

Muestra la fecha de inicio y caducidad de los certificados.

Después de regenerar: sudo systemctl restart gvmd gsad.

7. Base de datos

sudo runuser -u _gvm -- gvmd --migrate

Aplica migraciones de esquema de la base de datos. Necesario tras actualizar gvmd a una versión nueva. Ejecútalo con gvmd detenido (sudo systemctl stop gvmd).

sudo runuser -u _gvm -- gvmd --optimize=vacuum

Mantenimiento de la BD (compactar). Confirma las opciones disponibles con gvmd --help.

Respaldo

sudo mkdir -p /var/backups/gvm
sudo runuser -u _gvm -- pg_dump -d gvmd | gzip | sudo tee /var/backups/gvm/gvmd-$(date +%F).sql.gz >/dev/null

Guarda un dump comprimido (tareas, targets, reportes, usuarios).

sudo tar czf /var/backups/gvm/gvm-files-$(date +%F).tgz /var/lib/gvm/CA /var/lib/gvm/private /etc/gvm /etc/openvas

Respalda certificados y configuración.

Restauración (probar antes en una VM)

sudo systemctl stop gsad gvmd notus-scanner ospd-openvas
sudo runuser -u postgres -- dropdb gvmd
sudo runuser -u postgres -- createdb -O _gvm gvmd
gunzip -c /var/backups/gvm/gvmd-AAAA-MM-DD.sql.gz | sudo runuser -u postgres -- psql -d gvmd
sudo runuser -u _gvm -- gvmd --migrate
sudo gvm-start

Borra la base actual, la recrea y carga el respaldo.

8. Reparación: problema → solución

Reparación general (en orden)

# 1) parar los servicios de GVM
sudo systemctl stop gsad gvmd notus-scanner ospd-openvas

# 2) borrar residuos (pid y sockets viejos)
sudo rm -f /run/gvmd/gvmd.pid /run/ospd/ospd-openvas.pid /run/gvmd/gvmd.sock /run/ospd/ospd-openvas.sock

# 3) recrear carpetas de /run y corregir dueños
sudo systemd-tmpfiles --create
sudo chown -R _gvm:_gvm /var/lib/gvm /var/lib/openvas /var/lib/notus /var/log/gvm

# 4) asegurar PostgreSQL, Redis y MQTT
sudo systemctl start postgresql redis-server@openvas mosquitto

# 5) migrar la BD y regenerar certificados
sudo runuser -u _gvm -- gvmd --migrate
sudo runuser -u _gvm -- gvm-manage-certs -a -f

# 6) sincronizar feeds
sudo runuser -u _gvm -- greenbone-feed-sync

# 7) levantar y comprobar
sudo gvm-start
sudo gvm-check-setup

Fijar el "Feed Import Owner" (si los scan configs no se importan)

ADMIN_UUID=$(sudo runuser -u _gvm -- gvmd --get-users --verbose | awk '$1=="admin"{print $2}')
sudo runuser -u _gvm -- gvmd --modify-setting 78eceaec-3385-11ea-b237-28d24461215b --value "$ADMIN_UUID"

Indica a gvmd qué usuario será dueño de los datos importados del feed (configs, listas de puertos, formatos de reporte). Sin esto, esos datos pueden no aparecer.

Error: Failed to find config 'daba56c8-73ec-11df-a475-002264764cea'

Qué significa: ese UUID es el scan config "Full and fast", el que GSA deja preseleccionado al crear una tarea. El mensaje dice que gvmd no lo encuentra en su base de datos, es decir, los scan configs todavía no se han importado del feed (o nunca se importaron). El foro de Greenbone apunta además a que la base SCAP debe estar disponible.

Causas habituales: feed gvmd-data sin sincronizar, importación aún en curso, "Feed Import Owner" sin fijar, o feeds scap/nvt incompletos.

Diagnóstico:

sudo runuser -u _gvm -- psql -d gvmd -c "SELECT uuid, name FROM configs;"
sudo runuser -u _gvm -- psql -d gvmd -tAc "SELECT count(*) FROM nvts;"
sudo runuser -u _gvm -- psql -d gvmd -tAc "SELECT count(*) FROM scap.cves;"

Si la primera consulta no devuelve filas (o no aparece daba56c8-...), es esto. Si nvts o scap.cves dan 0, esos feeds tampoco se han importado.

Solución, en orden:

# 1) fijar el dueño de los datos del feed
ADMIN_UUID=$(sudo runuser -u _gvm -- gvmd --get-users --verbose | awk '$1=="admin"{print $2}')
sudo runuser -u _gvm -- gvmd --modify-setting 78eceaec-3385-11ea-b237-28d24461215b --value "$ADMIN_UUID"

# 2) sincronizar todos los feeds
sudo runuser -u _gvm -- greenbone-feed-sync

# 3) reiniciar para que gvmd detecte los datos
sudo systemctl restart ospd-openvas gvmd

# 4) esperar la importación (Ctrl+C para salir)
while true; do sudo runuser -u _gvm -- psql -d gvmd -tAc "SELECT (SELECT count(*) FROM nvts) AS nvts, (SELECT count(*) FROM configs) AS configs, (SELECT count(*) FROM scap.cves) AS cves;"; sleep 30; done

Cuando configs sea mayor que 0 y la consulta de arriba muestre "Full and fast", cierra sesión en GSA y recarga con Ctrl+F5.

Si configs ya tiene filas pero el error sigue: el ajuste de usuario del scan config por defecto apunta a uno inexistente. En GSA entra a los ajustes del usuario (My Settings → Defaults) y elige un Scan Config que exista.

Si pasada más de una hora sigue vacía: revisa sudo tail -n 100 /var/log/gvm/gvmd.log y, como último recurso, la sección 11 (reinicio de la base de datos).

10. Acceso remoto a la web (opcional)

Por defecto gsad solo escucha en 127.0.0.1.

systemctl cat gsad

Copia la línea ExecStart= original.

sudo systemctl edit gsad

Pega esto, cambiando solo la dirección de escucha en tu línea original:

[Service]
ExecStart=
ExecStart=<tu línea original, con --listen=0.0.0.0>

Luego: sudo systemctl restart gsad. Solo en redes de confianza; no expongas GSA a Internet. Si no quieres abrir el puerto, usa un túnel SSH: ssh -L 9392:127.0.0.1:9392 usuario@kali.

11. Reinicio total / desinstalación

Reiniciar solo la base de datos (conserva los paquetes)

sudo systemctl stop gsad gvmd notus-scanner ospd-openvas
sudo runuser -u postgres -- psql -c 'DROP DATABASE IF EXISTS gvmd;'
sudo gvm-setup

Borra tareas, targets, reportes y usuarios. gvm-setup recrea todo y genera una contraseña nueva de admin.

Desinstalar por completo

sudo systemctl stop gsad gvmd notus-scanner ospd-openvas
sudo runuser -u postgres -- psql -c 'DROP DATABASE IF EXISTS gvmd;'
sudo apt purge gvm gvmd gsad openvas-scanner ospd-openvas notus-scanner
sudo apt autoremove --purge
sudo rm -rf /var/lib/gvm /var/lib/openvas /var/lib/notus /var/log/gvm

Elimina paquetes, base de datos y datos. Es destructivo e irreversible.

13. Flujo rápido de un día normal

sudo gvm-start                                              # 1. levantar
sudo runuser -u _gvm -- greenbone-feed-sync                 # 2. actualizar feeds
sudo gvm-check-setup                                        # 3. comprobar
# ... trabajar en https://127.0.0.1:9392 ...
sudo gvm-stop                                               # 4. al terminar

Escanea únicamente sistemas que sean tuyos o para los que tengas autorización por escrito.

Pulsa «Copiar» en cualquier bloque de código. Escanea únicamente sistemas con autorización.
