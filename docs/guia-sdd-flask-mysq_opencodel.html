Commands, skills y Spec Driven Development

Guía práctica con un proyecto completo: app de tareas en Python, Flask y MySQL, adaptada a OpenCode. Todos los bloques tienen botón para copiar.

Custom commands

De dónde sale el prompt: lo escribes tú. Cada vez que repitas un prompt, guárdalo en un archivo .md; el nombre del archivo es el nombre del comando. $ARGUMENTS se reemplaza por lo que escribas después.

.opencode/commands/revisar.md
---
description: Revisa un archivo buscando bugs y fallos de seguridad
---
Revisa $ARGUMENTS buscando:
1. Bugs lógicos
2. Seguridad (SQL injection, secretos en el código)
3. Falta de manejo de errores
Responde con una lista priorizada y el fix de cada punto.

Uso: /revisar app/routes.py. Carpeta del proyecto (se comparte por git) o ~/.config/opencode/commands/ (personales). El nombre del archivo es el nombre del comando.

ElementoQué hace en OpenCode
$ARGUMENTSTodo lo que escribes tras el comando. También existen $1, $2... para argumentos posicionales.
@archivoIncluye el contenido de ese archivo en el prompt (ej. @specs/spec.md).
!`comando`Ejecuta un comando de shell e inserta su salida en el prompt (ej. !`git diff`).
Frontmatterdescription (se ve en el menú), agent (qué agente lo ejecuta), model (modelo a usar).
Versiones: la documentación actual usa la carpeta commands/ (plural). Versiones antiguas de OpenCode usaban command/ (singular). Si tu comando no aparece al escribir /, prueba con el otro nombre de carpeta y reinicia OpenCode.

¿Plantillas? No hay un catálogo oficial único. Hay repositorios de la comunidad para inspirarte, pero lo útil es crear los tuyos desde tus propios prompts repetidos. Las plantillas de esta guía son un buen punto de partida.

Skills

Una carpeta con un SKILL.md (y opcionalmente scripts o plantillas) que el agente carga solo cuando la tarea coincide con su description. Escribe esa descripción pensando en cuándo debe activarse.

.opencode/skills/endpoints-flask/SKILL.md
---
name: endpoints-flask
description: Usar al crear o modificar endpoints REST de Flask en este proyecto
---
- Todo endpoint va en un Blueprint dentro de app/routes/
- Valida la entrada antes de tocar la base de datos
- SQL siempre parametrizado, nunca f-strings
- Errores con el formato {"error": "mensaje"} y código HTTP correcto

¿Se inventan? Sí, sobre todo los que reflejan reglas de tu proyecto. El formato SKILL.md es un estándar abierto, así que sirven ejemplos de otras herramientas (como github.com/anthropics/skills). OpenCode los busca en .opencode/skills/, y también lee .claude/skills/ y .agents/skills/ si ya los tienes. El agente ve la lista de skills disponibles y carga el que coincide con su description.

Regla para elegir: ¿lo quieres disparar tú en un momento concreto (/spec)? Command. ¿Es conocimiento que el agente debe aplicar solo cuando toque (cómo hacemos endpoints)? Skill. ¿Es una regla que aplica siempre? AGENTS.md.

Qué es Spec Driven Development

En vez de pedir "hazme una app de tareas", escribes una especificación y el código se deriva de ella. La spec es la fuente de verdad. Los agentes fallan cuando adivinan, y una spec revisada elimina las adivinanzas antes de gastar tiempo en código.

FaseRespondeArchivoLo revisas buscando
Principios¿Con qué reglas trabajamos?AGENTS.mdStack, estilo, seguridad
Spec¿Qué y por qué? (sin tecnología)specs/spec.mdCriterios verificables, alcance
Plan¿Cómo? (técnico)specs/plan.mdCada criterio tiene dónde cumplirse
Tareas¿En qué orden?specs/tasks.mdPasos pequeños y verificables
ImplementarCódigo + testsapp/, tests/Diff y tests en verde

La regla de oro: revisa y corrige cada documento antes de pasar al siguiente. Un error en la spec cuesta una línea; en el código cuesta una tarde.

La base que necesitas para cualquier proyecto

Antes de ejecutar /spec, junta estos datos. Con ellos puedes iniciar un proyecto de cualquier tamaño; si no los tienes, el agente los preguntará, pero llegarás más rápido si los traes.

brief.md (plantilla universal)
# Brief: [nombre del proyecto]
1. Qué: una frase de lo que hace
2. Para quién: usuarios y su situación
3. Funcionalidades deseadas: lista de lo que debe poder hacerse
4. Fuera de alcance: lo que NO se hará (en esta versión)
5. Restricciones técnicas: lenguaje, base de datos, hosting, librerías
6. Restricciones no técnicas: plazo, presupuesto, normativa
7. Datos: qué información se guarda y cuál es sensible
8. Seguridad y acceso: quién puede hacer qué
9. Criterio de éxito: cómo sabré que está terminado
10. Dudas abiertas: lo que aún no he decidido

Ese brief es lo que pasas como argumento a /spec. Para el ejemplo, queda así:

Brief del ejemplo
Qué: API web para gestionar tareas personales
Para quién: una persona sola, uso local
Funcionalidades: crear, listar, completar y eliminar tareas
Fuera de alcance: login, fechas límite, categorías, interfaz elaborada
Restricciones: Python 3.12, Flask, MySQL 8, tests con pytest
Datos: título (obligatorio), descripción (opcional); nada sensible
Éxito: los 4 flujos funcionan y tienen tests que pasan
Dudas: ninguna por ahora

1. AGENTS.md (principios)

En OpenCode el archivo de reglas del proyecto es AGENTS.md. Puedes generarlo con /init y luego editarlo con lo siguiente, o escribirlo directamente. Si ya tienes un CLAUDE.md, OpenCode lo usa como respaldo cuando no existe AGENTS.md.

AGENTS.md
# Proyecto: todo-app

## Stack
- Python 3.12, Flask 3, MySQL 8 con mysql-connector-python
- Tests con pytest

## Reglas
- SQL siempre parametrizado (%s), nunca concatenar ni f-strings
- Credenciales solo en variables de entorno (.env); nunca en el código ni en git
- Validar toda entrada antes de tocar la base de datos
- Errores en JSON: {"error": "mensaje claro"} con el código HTTP correcto
- Código simple: sin patrones ni capas que no hagan falta
- Cada función de ruta hace una sola cosa

## Flujo de trabajo
- Seguir el método SDD: specs/spec.md -> specs/plan.md -> specs/tasks.md
- No escribir código fuera de lo que pida la tarea actual
- Si algo es ambiguo, preguntar antes de asumir
- Todo cambio de comportamiento se refleja primero en la spec

## Comandos útiles
- Ejecutar: flask --app app run --debug
- Tests: pytest -q

2. Los cuatro comandos

Crea la carpeta .opencode/commands/ y estos cuatro archivos. Todos deben ejecutarse con el agente build (el predeterminado), porque necesitan escribir archivos; el agente plan solo analiza. Son genéricos: sirven igual para cualquier otro proyecto.

.opencode/commands/spec.md
---
description: Genera specs/spec.md a partir de un brief
---
Lee AGENTS.md y crea specs/spec.md para este brief:

$ARGUMENTS

Reglas:
- Solo el QUÉ y el POR QUÉ. Prohibido mencionar tecnologías, tablas o rutas.
- Secciones: Objetivo, Usuarios, Historias de usuario, Criterios de
  aceptación, Reglas de negocio, Fuera de alcance, Dudas abiertas.
- Numera historias (HU-1...) y criterios (CA-1...). Cada criterio debe ser
  verificable: alguien debe poder decir "cumple" o "no cumple".
- Si algo del brief es ambiguo, NO lo asumas: anótalo en Dudas abiertas
  y pregúntame antes de continuar.
.opencode/commands/plan.md
---
description: Genera specs/plan.md a partir de la spec
---
Lee specs/spec.md y AGENTS.md. Crea specs/plan.md con:
1. Arquitectura y estructura de carpetas
2. Esquema de base de datos (SQL completo)
3. Contrato de endpoints: método, ruta, entrada, salida, errores
4. Validaciones y formato de errores
5. Configuración (variables de entorno)
6. Estrategia de pruebas
7. Decisiones técnicas y su razón
8. Tabla de trazabilidad: cada CA de la spec -> dónde se cumple
No escribas código de implementación. Si un CA no tiene dónde cumplirse,
avísame.
.opencode/commands/tasks.md
---
description: Genera specs/tasks.md a partir del plan
---
Lee specs/plan.md y crea specs/tasks.md.
Cada tarea: id (T1, T2...), descripción de una línea, archivos que toca,
criterios CA que cubre, cómo verificarla, y dependencias.
Reglas: tareas pequeñas (menos de ~1 hora), ordenadas, cada una deja el
proyecto funcionando. Formato con casilla: - [ ] T1 ...
Los tests van dentro de la tarea que prueban, no al final.
.opencode/commands/implement.md
---
description: Implementa UNA tarea de specs/tasks.md
---
Implementa SOLO la tarea $ARGUMENTS.
1. Lee specs/spec.md, specs/plan.md, la tarea en specs/tasks.md y AGENTS.md.
2. Verifica que sus dependencias estén marcadas [x]; si no, detente y avísame.
3. Escribe primero los tests de la tarea, luego el código.
4. Ejecuta pytest. Si falla, corrige hasta que pase.
5. Marca la tarea con [x] y resume: archivos cambiados y tests que pasan.
Reglas: no toques código ajeno a la tarea. Si descubres que la spec o el
plan están mal o incompletos, detente y propón el cambio en el documento
en lugar de improvisar en el código.

3. specs/spec.md (cómo lo escribiría)

Ejecuta /spec con el brief del ejemplo. Este es el resultado que yo consideraría bueno; tu versión será parecida y la ajustas a mano.

specs/spec.md
# Spec: Gestor de tareas personales

## Objetivo
Permitir a una persona registrar sus tareas pendientes y saber cuáles
ha completado, para no olvidar lo que tiene que hacer.

## Usuarios
Una sola persona usando la aplicación en su equipo. No hay cuentas.

## Historias de usuario
- HU-1: Como usuario quiero crear una tarea con un título y una
  descripción opcional, para registrar algo pendiente.
- HU-2: Como usuario quiero ver todas mis tareas, para saber qué
  tengo por hacer.
- HU-3: Como usuario quiero marcar una tarea como completada, para
  distinguir lo hecho de lo pendiente.
- HU-4: Como usuario quiero eliminar una tarea, para quitar lo que
  ya no es relevante.

## Criterios de aceptación
- CA-1: Una tarea nueva requiere título; sin título o con solo espacios
  se rechaza con un mensaje claro.
- CA-2: El título admite como máximo 100 caracteres; más se rechaza.
- CA-3: La descripción es opcional.
- CA-4: Toda tarea nueva nace como pendiente.
- CA-5: El listado muestra todas las tareas, la más reciente primero.
- CA-6: El listado indica de cada tarea título, descripción, estado
  y fecha de creación.
- CA-7: Completar una tarea ya completada no produce error y la deja
  completada.
- CA-8: Completar o eliminar una tarea que no existe produce un error
  claro de "no encontrada".
- CA-9: Una tarea eliminada no vuelve a aparecer en el listado.
- CA-10: Las tareas persisten aunque se reinicie la aplicación.

## Reglas de negocio
- El título se guarda sin espacios sobrantes al inicio y al final.
- Una tarea solo pasa de pendiente a completada (no se desmarca).

## Fuera de alcance (esta versión)
Usuarios y login, fechas límite, categorías, edición del título,
búsqueda, paginación, interfaz elaborada.

## Dudas abiertas
- ¿Se debe poder desmarcar una tarea completada? (asumido: no, ver
  Reglas de negocio; confirmar)
Revisión de la spec: ¿hay tecnología? (no debe haber). ¿Cada CA se puede probar con "cumple/no cumple"? ¿Falta algún caso de borde? Responde las dudas abiertas aquí, antes de seguir.

4. specs/plan.md (cómo lo escribiría)

specs/plan.md
# Plan técnico: Gestor de tareas

## 1. Arquitectura
Aplicación Flask con application factory y un Blueprint. Acceso a MySQL
con funciones simples en app/db.py (sin ORM, para mantenerlo sencillo).
Una página HTML mínima servida por Flask que consume la API con fetch.

## 2. Estructura
todo-app/
  app/
    __init__.py      # create_app(), registra el blueprint
    db.py            # get_connection(), init_db()
    routes.py        # blueprint "tareas"
    templates/index.html
  schema.sql
  tests/
    conftest.py      # cliente de prueba y BD de test limpia
    test_tareas.py
  .env.example
  requirements.txt
  README.md

## 3. Base de datos
CREATE TABLE IF NOT EXISTS tareas (
  id          INT AUTO_INCREMENT PRIMARY KEY,
  titulo      VARCHAR(100) NOT NULL,
  descripcion TEXT NULL,
  completada  BOOLEAN NOT NULL DEFAULT FALSE,
  creada_en   TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);

## 4. Endpoints
| Método | Ruta                    | Entrada (JSON)             | Éxito            | Errores        |
|--------|-------------------------|----------------------------|------------------|----------------|
| GET    | /                       | -                          | 200 HTML         | -              |
| GET    | /api/tareas             | -                          | 200 lista JSON   | -              |
| POST   | /api/tareas             | titulo, descripcion?       | 201 tarea creada | 400            |
| PATCH  | /api/tareas//completar | -                       | 200 tarea        | 404            |
| DELETE | /api/tareas/        | -                          | 204 sin cuerpo   | 404            |

Objeto tarea: {id, titulo, descripcion, completada, creada_en}
Listado ordenado por creada_en DESC, id DESC.

## 5. Validaciones y errores
- titulo: string, strip(); vacío -> 400; más de 100 -> 400
- descripcion: string o null
- Formato de error: {"error": "mensaje"}
- 404: {"error": "Tarea no encontrada"}

## 6. Configuración (.env)
DB_HOST, DB_PORT, DB_USER, DB_PASSWORD, DB_NAME
Los tests usan DB_NAME=todo_test.

## 7. Pruebas
pytest con cliente de Flask. Cada test parte de la tabla vacía.
Un test por criterio de aceptación relevante.

## 8. Decisiones
- Sin ORM: son 4 consultas; menos dependencias y más claro.
- PATCH /completar en vez de PUT genérico: refleja la acción de negocio
  y evita edición accidental de otros campos.
- Completar es idempotente (CA-7): UPDATE sin error si ya está completa.
- 204 en DELETE: no hay nada que devolver.

## 9. Trazabilidad
| CA        | Se cumple en                                       |
|-----------|----------------------------------------------------|
| CA-1,2,3  | Validación en POST /api/tareas                     |
| CA-4      | DEFAULT FALSE en la tabla                          |
| CA-5,6    | GET /api/tareas con ORDER BY creada_en DESC        |
| CA-7,8    | PATCH /api/tareas//completar                   |
| CA-8,9    | DELETE /api/tareas/                            |
| CA-10     | Persistencia en MySQL                              |
Revisión del plan: ¿la tabla de trazabilidad cubre todos los CA? ¿Las decisiones tienen razón? ¿Hay algo que la spec no pidió y el plan agregó? Si es así, quítalo o súbelo a la spec.

6. Implementar, una tarea por vez

Antes: crea la base de datos de desarrollo y la de test en MySQL y llena tu .env.

Sesión de trabajo
/implement T1
  -> revisas el diff, corres pytest -q, haces commit
/implement T2
  -> revisas, pruebas, commit
/implement T3
  ...

Checklist de revisión después de cada tarea:

  • El diff solo toca archivos de la tarea.
  • pytest -q pasa y los tests prueban el criterio, no solo "que corra".
  • No hay SQL concatenado ni credenciales escritas en el código.
  • La tarea quedó con [x] y haces un commit por tarea.

Si el agente se detiene diciendo que la spec o el plan están incompletos, eso es una buena señal del método: corrige el documento, no improvises en el código.

7. Cuando algo cambia

Ejemplo: quieres fecha límite en las tareas. El orden es siempre el mismo:

Flujo de un cambio
1. Edita specs/spec.md: nueva HU-5, nuevos CA (formato de fecha,
   si es obligatoria, qué pasa con fechas pasadas). Revisa.
2. /plan   -> actualiza plan.md (columna en BD, cambios en endpoints)
3. /tasks  -> agrega tareas nuevas (ej. T9 migración, T10 POST con fecha)
4. /implement T9, /implement T10 ...

Así la documentación nunca queda desfasada del código, que es el objetivo de todo el método.

Opcional y muy útil: un comando /clarify que lea la spec y te haga preguntas sobre lo ambiguo antes de planificar.

.opencode/commands/clarify.md
---
description: Detecta ambigüedades en la spec
---
Lee specs/spec.md. Lista hasta 8 preguntas sobre casos de borde, reglas
no definidas o criterios no verificables. Hazlas una por una y, con mis
respuestas, actualiza la spec.

Chuleta

Resumen
AGENTS.md  -> reglas permanentes (siempre cargado)
Command    -> prompt que TÚ invocas (/nombre)
Skill      -> conocimiento que el AGENTE carga solo

SDD: Brief -> /spec (qué) -> /plan (cómo) -> /tasks -> /implement T#

Reglas:
 · Revisar cada documento antes de avanzar
 · Una tarea por vez, con tests y un commit
 · Los cambios empiezan en la spec, no en el código
 · Si es ambiguo, preguntar; no asumir
 · Cada criterio de aceptación debe ser verificable
 · Cada CA debe tener dónde cumplirse (trazabilidad)

Errores comunes:
 × Meter tecnología en la spec
 × Tareas gigantes ("implementar la API")
 × Saltarse la revisión porque "se ve bien"
 × Arreglar el código sin actualizar la spec
